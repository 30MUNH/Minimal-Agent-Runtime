Design Rationale & Architecture Principles

A comprehensive overview of key design choices behind the Minimal Agent Runtime architecture.

1. Agent Loop

AgentRuntime.run(task) starts one run-level working memory transcript initialized with the user task. Each loop iteration sends the current messages transcript plus generic tool definitions to the configured model provider. The provider returns a normalized ModelReply: either a final answer or a structured tool call request.

For a tool call, the runtime records the model request, looks up the tool by name, executes it, appends a structured observation (tool_result or tool_error) to both the trace and the transcript, then calls the model again. Unknown tools, invalid arguments, and tool exceptions become observations so the model can recover gracefully.

2. Tool Interface

Each Tool exposes name, description, a JSON input schema, and a handler executed by run(args). The runtime only knows this generic interface; there are no tool-specific branches in the orchestration loop.

The registry is a dictionary keyed by tool name. Filesystem tools (list_files, read_file, write_file, search_files) are strictly bounded to workspace/. Memory tools (remember, recall) expose persistent memory explicitly to the model.

3. Memory Dual Architecture

Working Memory: The in-memory transcript for one execution (user task, model replies, tool calls, and tool observations). Discarded after run() returns.

Persistent Memory: Backed by JsonMemory, a JSON key/value store surviving process restarts. The model accesses it through explicit remember(key, value) and recall(key) tools, ensuring cross-run facts are deliberate rather than dumping raw history into every prompt context.

4. Observability & Tracing

Execution tracing exists so reviewers can see the think-act-observe cycle without reading raw Python objects. The runtime records model invocations, tool requests, tool outcomes, termination reasons, and per-tool durations in the same trace used by tests and CLI output.

Structured JSON logs make a run inspectable after the fact: task, provider, steps, tool calls, observations, timings, final answer, and stop reason are stored safely without leaking secrets.

5. Termination Guarantees

The runtime enforces strict bounds on execution loops via max_steps (default 8 in runtime, 12 in CLI). Execution terminates under two conditions:

  • final: Model returns a final textual answer.
  • max_steps: Maximum step limit reached without final answer, returning current trace and step limit status.
